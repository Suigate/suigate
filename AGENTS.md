# suigate

## Scope and dependencies

- The implementation consists of the Move package in `move/suigate`, `@suigate/core`, `@suigate/react`, `@suigate/express`, `@suigate/nextjs`, the `suigate` CLI in `packages/cli`, and React/Express/Next.js examples. Product documentation is in `README.md` and `docs/`.
- Use the official Sui `testnet-v1.81.0` toolchain (verified CLI version: `1.81.0-bf0c491c17b8`).
- Payment Kit is pinned to commit `34464974de849975872cc67f02715a98db3112ba` in `Move.toml`. Keep the generated `Move.lock` in source control; do not hand-edit it.
- `std` and `sui` are implicit framework dependencies. Mainnet and testnet dependency resolutions are locked independently.
- Do not publish packages or execute transactions on public networks as part of ordinary testing.

## Contract invariants

- Payment Kit processes payments inside `purchase` and `renew`; there is no separately callable unpaid entitlement mint.
- Each Service creates its own shared, direct-payment registry. Its Payment Kit admin capability remains wrapped inside the non-publicly-transferable ServiceAdminCap.
- Configuration changes require both the matching capability and the current owner. Transferring service administration does not automatically change the payment recipient.
- Plan keys are case-sensitive, nonempty ASCII strings of at most 64 bytes. Prices are coin base units; durations and timestamps are milliseconds. Service configuration versions, plan versions, and entitlement revisions are separate counters.
- Entitlements are address-owned with `key` only, non-transferable, and unique per Service/holder/plan. Do not add `store`, burn, or public transfer support without revisiting uniqueness and authorization.
- Payment Kit receipts are copyable values/events, not owned entitlements or one-use proofs. Payment records are deletable; derived issuance claims and renewal revision checks protect lifecycle operations after record cleanup.
- Revocation is permanent in this version and is stored on Service, not by mutating the customer's object. Purchase/renewal availability does not invalidate already purchased time.
- Move expected-failure tests cannot inspect state after an abort. For rollback validation, use an isolated local network: execute two purchases for one holder/plan in a PTB, then two renewals with the same expected revision in a PTB. Check unchanged merchant funds and entitlement data, no committed events, and successful retry of the first operation's nonce. Failed transactions still charge gas and can advance object versions even when Move fields are unchanged.

## TypeScript core

Use Node 24 LTS (verified with 24.13.0). The host's Node 23 does not satisfy the transitive GraphQL package's supported engine range. Core pins `@mysten/sui` 2.33.2 as a peer, `@mysten/payment-kit` 0.2.31, and `@mysten/bcs` 2.1.2. The repository now uses npm workspaces: install from the root and use the root `package-lock.json` so React, dApp Kit, and the Sui SDK have shared runtime identities. The original core-only lockfile is retained but is not the workspace installation entry point.

```sh
npm ci --ignore-scripts
npm run check
npm run format:check -w @suigate/react
npm run dev
npm pack -w @suigate/react --dry-run
```

`npm run check` builds core, React, Express, Next.js, and the example and runs all TypeScript tests. `npm test` and `npm run dev` first build the local library dependencies. To use Node 24 without changing the host's active version, prefix commands with `npm exec --yes --package=node@24.13.0 --call`, for example `npm exec --yes --package=node@24.13.0 --call 'npm run check'`.

- Configure `SuigateClient` with a caller-owned `ClientWithCoreApi`, trusted `packageId`, and expected full genesis `chainIdentifier`. Set `typeOrigin` separately when the call package has been upgraded. The pinned Payment Kit extension supports mainnet and testnet only.
- Purchase and renewal methods return unsigned `Transaction` builders, deterministic entitlement IDs, and quote snapshots. They do not execute payments or assert that an entitlement has been issued. Only suigate's atomic Move wrapper is called. Fetch state after successful execution and indexing to confirm the result.
- Renewals require `expectedRevision`. Persist the built transaction/quote and nonce for retries; do not silently rebuild a timed-out renewal against a newer revision.
- BCS schemas must stay aligned with the Move layouts. Prices, timestamps, durations, and contract counters use bigint. Never authorize using caller-provided entitlement fields.
- `getEntitlement` can cache discovery snapshots for up to five seconds by default, bounded by entitlement expiry. `verifyEntitlement` and renewal always bypass that cache, reread ownership, and check the Service revocation table. Keep the server clock synchronized and use a trusted, current Sui provider.
- The internal Payment Kit adapter delegates record encoding/decoding to the official SDK. Version 0.2.31's generated `PaymentKey.name` includes the literal `<phantom T>`, producing an invalid lookup type. A narrowly scoped client proxy removes that placeholder; do not replace it with a custom receipt/registry implementation. A live testnet read-only lookup validated the correction.
- `gas: "auto"` chooses a configured sponsor or user gas. Gas settings remain unset for SDK resolution when user-paid, preserving genuine protocol zero-fee detection for eligible PTBs. Entitlement writes are not eligible for gasless stablecoin transfers. Configure sponsorship before adding inputs/commands; sponsored SUI payments must use customer-funded coins, never the sponsor's gas coin. Sponsors must validate the final transaction and both parties must sign the same bytes.
- Authentication helpers run on the backend. `verifySignature` verifies the Sui personal-message intent; it alone does not provide replay protection. Use `createChallenge`/`verifyChallenge` for authentication. Verification takes only a stored challenge ID and signature plus trusted server-supplied expected context, not a client-provided message.
- Bind challenges to audience origin, wallet, Service, chain, and an opaque request/session binding. Do not use a session secret as the binding. Default TTL is five minutes, the maximum. The default challenge store is process-local; multi-instance deployments must inject a shared store whose `consumeIfUnexpired` operation atomically checks expiration and consumes exactly once. No database or Redis is required for single-process use.

## React paywall and example

- Use the current `@mysten/dapp-kit-react` 2.1.37 and `@mysten/dapp-kit-core` 1.6.35 APIs, not legacy `@mysten/dapp-kit`. Workspace overrides pin the compatible core, Wallet Standard 0.21.31, and Slush 1.3.1 dependency cohort against Sui 2.33.2. React is pinned to 19.3.0.
- Application setup is the official `DAppKitProvider`, then `SuigateProvider deployment={{ network, packageId, chainIdentifier }}`, then `<SuigatePaywall serviceId={serviceId} plan="pro" />`. The paywall uses the official `ConnectButton` and `signTransaction` action. Do not introduce wallet adapters or private-key handling into this package.
- `useSuigatePurchase` is the headless React API. Framework-independent UIs can use the existing `SuigateClient.purchaseEntitlement` in core. The paywall verifies exact wallet-signed bytes, submits with the Sui Core API, waits for the computed digest, checks the entitlement creation effect, and calls core's live entitlement verifier before reporting success.
- Current Move plans accept exactly one coin type. `coinType`, `onCoinTypeChange`, and `renderCurrency` allow selection controls, but unsupported currencies are rejected. Alternative currencies require corresponding on-chain plan support; the React package does not invent exchange rates or swap tokens.
- Customization includes labels, root class/style, currency/loading/success/error renderers, and success/error/state callbacks. The default UI shows the active Sui network and describes gas as a network fee, never as a free stablecoin entitlement transaction.
- Optional `sponsorship` contains a core `Sponsor` configuration and an async `sign` callback. The callback receives final transaction bytes and returns only a sponsor signature; the frontend verifies that signature against the configured sponsor. Keep signing keys and sponsorship policy on the server. Both customer and sponsor sign exactly the same bytes. No sponsor server is implemented here.
- Unknown execution or confirmation results retain the computed digest in memory and offer status checking, not a new payment. Pending state is scoped to wallet/network/service/plan and is not persisted across page reloads. Account/configuration changes before submission prevent the old checkout from executing. Changed plan terms require another explicit approval.
- `examples/react` is a configurable Vite app and defaults to the actual public testnet endpoint. Package and Service IDs are intentionally blank. Optional public configuration is listed in its `.env.example`; never put signing keys in `VITE_*` variables. Opening the example does not submit transactions. Purchases require configuring a deployed service and approving with a wallet.
- Automated UI tests run in jsdom with real dApp Kit/Wallet Standard interfaces, a test wallet, real test signatures, and mocked chain responses. External fetches are blocked. They are neither localnet integration tests nor live testnet/mainnet purchases.
- Vitest must resolve browser exports and inline Lit/dApp Kit dependencies for jsdom; otherwise Lit's Node/SSR React adapter does not assign the wallet instance to web components. Do not hide the resulting unhandled errors by mocking away the production connection component.
- React/example TypeScript source remains strict with exact optional properties. `skipLibCheck` is enabled only for third-party declarations, which currently contain incompatible optional-property declarations in dApp Kit's modal and Wallet Standard's account class. Core retains its existing stricter declaration checking.
- Vite currently reports a large wallet/SDK bundle warning and an upstream `@scure/base` pure-annotation warning; these are non-failing build warnings, not failed tests.

## Backend authorization

- Express targets 5.2.1; Next.js targets 16.3.8. These exact, aged releases are pinned. Next's installed guides are in `node_modules/next/dist/docs/`; use the `proxy.ts` convention and Promise-based Route Handler params from those guides.
- `SuigateAuthorizer` in `@suigate/core/server` owns HTTP authentication orchestration. It calls the existing core challenge/signature verifier and `SuigateClient.verifyEntitlement`; framework adapters must not implement their own ownership, plan, expiry, or revocation checks.
- Configure adapters with `client`, `packageId`, `chainIdentifier`, and `audience`, plus the required `serviceId` and `plan`. For the short two-field Express API, supply server environment variables `SUIGATE_NETWORK`, `SUIGATE_RPC_URL`, `SUIGATE_PACKAGE_ID`, `SUIGATE_CHAIN_IDENTIFIER`, and `SUIGATE_AUDIENCE`. Network and RPC URL are only needed when no client is injected. Missing configuration fails at construction; no network or deployment is silently selected. Audience is a trusted HTTP(S) origin, never inferred from Host or forwarded headers.
- Express: `app.use('/api', suiGate({ serviceId, plan }))` exposes `POST /api/.suigate/challenge` and gates other requests. The successful authorization context is `req.suigate`. To mount issuance elsewhere, retain the returned middleware, set `challengePath: false`, and register `app.post('/auth/challenge', gate.challenge)` before the protected routes. The middleware does not consume protected request bodies; applications install their own body parsers and CORS handling.
- Challenge JSON is `{ address, entitlementId, method: 'GET', target: '/api/data?query=value' }`. Target must be the canonical, origin-relative request path including its query; Express uses `originalUrl`, preserving mount prefixes. All fields are required, and client-selected service/plan fields are rejected. The response's random `id` is the nonce, `expiresAt` is in milliseconds, and `message` is the exact UTF-8 text to sign through the wallet's Sui personal-message API.
- Send the protected request with `Authorization: encodeAuthorizationProof({ challengeId: challenge.id, signature, address, entitlementId })`, using the helper exported by `@suigate/core`. Entitlement IDs and wallet addresses alone are never credentials. Proofs are bound to wallet, entitlement ID, service, plan, audience, chain, HTTP method, and target. They authenticate access, not application request-body contents; use TLS and validate/authorize application payloads separately.
- Proofs are single-use per request, not reusable login sessions. Consumption is atomic and occurs after signature verification but before entitlement lookup. A denied entitlement or later RPC failure can still consume a valid proof; obtain a fresh challenge for the next attempt. Never log proof headers. Issuance bodies are limited to 8 KiB, proof headers to 16 KiB, and challenges to at most five minutes.
- The default challenge store is bounded process-local memory. Keep one configured gate instance per policy and import it from shared server code. Multi-worker/serverless deployments need a shared `ChallengeStore` with atomic `consumeIfUnexpired`; Redis is not mandatory. Rate-limit the public issuance endpoint using the application's trusted ingress/IP policy.
- `cache`/`cacheTtlMs` pass through to the existing core cache abstraction. Every authorization decision still fetches current Sui state, so cached snapshots cannot hide renewals, revocations, ownership changes, or expiration. RPC/store failures fail closed.
- Responses use generic `401` for missing/invalid/expired/replayed proof, `403` for authenticated entitlement denial, and `503` for verification infrastructure failures. Challenge validation adds `400`, `405`, `413`, and `429`. Adapters enforce `private, no-store` and `Vary: Authorization` on protected responses; Express applies the policy again immediately before headers are written so downstream handlers cannot accidentally make them public.
- Next.js: create one `gate = createSuiGate(options)` in a server module. Export `POST = gate.challenge` from the challenge route and `GET = gate.withAuthorization(async (request, auth, context) => Response.json({ wallet: auth.address }))` from a protected route. `context.params` remains a Promise. Use Node runtime and keep authenticated routes/data dynamic; never put authorization inside `use cache`, `unstable_cache`, or `force-static` rendering.
- For Next server/data-access code, use `gate.authorizeRequest(request)` or `gate.authorize({ authorization, method, target })` with a trusted expected target. Call once and pass the resulting context to downstream functions; calling it twice consumes the same proof twice. This is not a cookie/session integration for ordinary browser page navigation.
- `suigateProofPreflight` from `@suigate/nextjs/proxy` is an optional, non-consuming format/presence check for Proxy. It is NOT authorization. Exclude challenge routes and static assets from its matcher, and always use definitive authorization in protected Route Handlers or server functions. No forwarded wallet/entitlement header is trusted.
- The main Next entry point imports `server-only`; the stateless Proxy subpath is separate. Next tests run with the real `react-server` module condition, not a mocked-away server-only marker. Next source is strictly checked; `skipLibCheck` only excludes inconsistent vendor declarations in Next's bundled Satori/Sharp/URLPattern types.
- Backend tests use real wallet signatures and core verification against mocked Sui object/RPC state. Express is exercised over loopback HTTP; Next uses real NextRequest/NextResponse objects. Renewal tests observe updated confirmed-state fixtures; they do not execute public-network transactions.

## CLI, examples, and documentation

- Keep local `.suigate/` deployment journals ignored, but preserve the explicit ignore exceptions for `examples/nextjs/app/api/.suigate/`: its discovery/OpenAPI routes are application source and must be tracked. Next.js generates `next-env.d.ts`; keep it ignored and included in tsconfig, not manually maintained. Retain `Move.lock`, npm lockfiles, public `.env.example` templates, and generated package README/NOTICE/LICENSE files in source control.

- `packages/cli` is the npm package `suigate`; its executable is `bin/suigate.mjs`. Build before using `npx --no-install suigate`. Do not publish packages or assume the registry's uninstalled package is this checkout.
- CLI commands: `init`, `deploy`, `plans`, `status`. Public project settings are in `suigate.config.json`; managed state/locks live under `.suigate/deployments/`. `init` defaults to testnet, 1 SUI / 30-day Pro access, detects package manager/framework and existing wallet context, and refuses overwrites. No keys are generated/imported/exported by suigate.
- Check that an existing Sui client configuration exists before invoking wallet commands. Never invoke wallet initialization implicitly. `SUI_BIN`/`--sui` select the native executable; `--sui-config` selects existing client configuration. Do not read keystores or ask for private keys.
- Sui CLI 1.81 rejects `--build-env` for publication, even though it appears among generic build options in help. `sui client publish` must derive its build environment from the explicitly selected `--client.env`; retain `--build-env` only for standalone Move build/test/lint commands. Regression tests assert publication does not pass this flag or bypass dependency verification. A real unsigned publish preparation against testnet verified the corrected invocation without signing/submitting.
- Native preparation failures occur before journaled submission and must not be described as uncertain execution. Keep the actual operation and safe allow-listed diagnostic category, but never echo raw native output, arbitrary arguments, RPC credentials, or recovery material. Pending digests still require reconciliation after submission errors.
- Sui CLI 1.81 unsigned/signed serialization must omit `--json`: with it, the CLI emits decoded transaction JSON instead of base64 BCS bytes. `client serialized-tx` reconstructs TransactionData and refreshes address-balance expiration nonces: NEVER submit through that command after journaling an unsigned digest. Use it only with `--serialize-signed-transaction`; decode/verify the final envelope, permit only the nonce refresh, journal the final signed digest, and submit unchanged bytes with `execute-combined-signed-tx --signed-tx-bytes`. Do not persist or log signed envelopes.
- Legacy pending publications recorded before the nonce bug fix can be recovered with `deploy --resume --recover-publish <confirmed-digest>`. Recovery requires matching sender, source fingerprint, exact compiled transaction kind and upgrade-cap recipient, retains the old digest in history, and never republishes. Do not auto-adopt a wallet's latest package or erase unknown pending state. A testnet publication was independently verified read-only during debugging; that does not establish a complete live purchase/API test.
- Deployment may require three transactions: publish, create Service, create all missing plans. Native `create_service` shares/transfers its outputs and returns no values, so initial plans cannot simply borrow those new objects in that same PTB. Preserve this distinction from atomic customer purchase.
- Preview wallet/network/source/terms/budgets before interactive confirmation. Never switch wallets/environments, skip dependency verification, or silently update existing live terms. Persist the final signed transaction digest before submission. Confirm/reconcile using the SDK Core API's typed effects and object types, not legacy CLI transaction JSON. An unavailable outcome remains pending; do not blindly repeat publication.
- Package builds copy canonical Move sources/manifest/lock into CLI dist assets. Do not hand-maintain a second contract source tree. `SuigateClient.listPlans` uses paginated dynamic fields and validates each plan; status output must read Sui, not merely print desired configuration.
- `SUI_NETWORKS` pins full mainnet/testnet chain identifiers and Payment Kit package/namespace bindings, cross-checked against the installed SDK and live read-only chain queries. Examples are testnet-only even though the CLI supports explicitly configured mainnet.
- `npm run build`/`npm run check` include the CLI and all three examples. `npm run dev:express` serves port 3001; `npm run dev` serves Vite with `/api` proxied to Express; `npm run dev:nextjs` runs the alternative full-stack demo on port 3000.
- Shared example checkout lives in `examples/shared/checkout.tsx`; server configuration loading uses only public deployment state or explicit server environment values. Free endpoints work without configuration; Pro and challenge endpoints fail closed. Purchase and subsequent API authentication are separate wallet approvals.
- Next/Turbopack source imports must resolve actual TypeScript modules: use extensionless Next-local imports and explicit `.ts` shared imports with `allowImportingTsExtensions`, not nonexistent sibling `.js` source files. The wallet UI is dynamically loaded client-side with SSR disabled; the built library imports remain `.js`.
- Keep `README.md` and `docs/` synchronized with command flags, one-use proof semantics, gas/currency limits, partial deployment recovery, and single-process example storage. Live wallet-approved testnet deployment/purchase remains separate from automated mock-based tests. Never imply the walkthrough has run on a public network unless it actually has.

## Agent discovery

- Discovery is opt-in via adapter `discovery: { path, challengePath, openApiPath, checkoutPath?, sponsorship? }`. Paths are explicit, canonical, same-origin and include mount prefixes; do not derive them from Host/forwarded headers. Express can route them automatically under its middleware mount or expose `gate.discovery`/`gate.openapi` manually. Next exposes those handlers for explicit Route Handler files.
- Core owns protocol-v1 JSON schema, OpenAPI 3.1 generation, path validation, and live discovery assembly. `DISCOVERY_SCHEMA`/`DiscoveryDocument` are public core exports. Metadata contains only public policy/chain terms, never RPC secrets, proof signatures or private keys. Terms are decimal-string snapshots, not executable quotes; builders must re-fetch authoritative terms.
- Preserve legacy error JSON/status behavior when discovery is disabled. Enabled failures append a `Link: rel="describedby"` and `suigate` extension: 401 authenticate, 403 inspect_entitlement, 429/503 retry_later, validation errors correct_request. Do not turn revocation, wrong objects or outages into automatic purchase/402 responses.
- `createSuigateProofPreflight({ discovery })` advertises the descriptor at an optional Proxy boundary without consuming a proof. It is still not authorization. Exclude all public protocol routes from Proxy matchers.
- `SuigatePaywall.discoveryUrl` adds a visible typed link and discovery/service/plan data attributes. Both example documents advertise `/api/.suigate/discovery` in initial HTML. Next wallet UI remains client-only, but discovery lives in the server layout head. Manual example checkout configurations must not be associated with another backend policy's descriptor.
- JSON Schema tests use pinned Ajv 8.20.0 as a dev-only dependency. Agent-flow tests start with an unauthenticated response and follow advertised endpoints through real signature verification and replay rejection. Discovery must not issue/consume challenges or construct/sign/submit payment transactions.
- This is a suigate-specific discovery protocol, not a registered well-known namespace or x402 implementation. It supplies information, never spending authority. Clients must enforce origin/contract allowlists, explicit approval or budgets, and safe/idempotent retries. The generated OpenAPI describes public protocol endpoints and reusable auth components, not fabricated business operations. See `docs/agent-discovery.md`.

## AI provenance, audit status, and risk warnings

- The publisher discloses the suigate implementation as 100% AI-generated. Current status is experimental and `humanAuditStatus: "not-audited"`, with no audit report/revision. Do not claim that tests, dependency scans, AI reviews, or successful transactions constitute a human audit. Third-party dependencies retain their own authorship/licenses.
- Canonical runtime disclosure/status lives in `packages/core/risk.mjs`, with types in `risk.d.mts`, exported from core and `@suigate/core/risk`. The self-reference subpath lets compiled tests and distributed runtime code share the same asset. Imports themselves do not log or perform side effects.
- `DISCLAIMER.md` contains the full AS-IS/no-warranty/liability notice and a human-reviewed-release checklist. Liability limitations are qualified by applicable law and must not be described as guaranteed immunity. Retain truthful AI provenance and appropriate warranty/liability language even after a documented audit.
- Root `npm run notices` regenerates marked package README/NOTICE files; root builds and root pretest run it automatically. Do not overwrite unmarked manually maintained documents. All five publishable packages include these files and machine-readable `suigateRisk` flags. Synchronize notices, runtime status, metadata, UI, and tests when a reviewed release changes audit status.
- Core and root postinstall hooks only print a warning; they do not access wallets, read keys, contact networks, prompt, or modify the environment. npm may hide dependency output, and ignore-scripts may disable it. Keep static/package/runtime notices regardless; never weaken script security policies merely to show a warning.
- CLI warnings go to stderr on every invocation. New deployment transactions require `--acknowledge-unaudited` plus the existing interactive confirmation and all wallet/network/gas checks. Dry-run and read-only reconciliation remain available without acknowledgement. The flag does not mark anything audited or guarantee legal enforceability.
- Paywall and example HTML display risk notices before wallet interaction. Agent discovery/OpenAPI and enabled error extensions expose `software` risk flags and the notice. No environment variable or command-line flag upgrades the audit status.
- Keep warnings until qualified humans review the exact release, document scope/findings/remediation and residual risk, and maintainers explicitly link the report and audited revision. Later material changes are not automatically covered. Never remove warnings just because a build/test passes.
